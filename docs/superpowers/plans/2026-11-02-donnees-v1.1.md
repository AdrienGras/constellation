# Données `metiers.json` v1.1 — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Objectif :** faire passer `metiers.json` en v1.1. Les trous de salaires sont comblés, éventuellement par rapprochement déclaré. Les codes ROME, les parcours et les liens roadmap.sh sont remplis. Les macro-branches et le quiz sont ajoutés. Enfin, `relecture.md` liste ce qu'Adrien doit vérifier.

**Architecture :** les agents de recherche n'écrivent jamais dans `metiers.json`. Chacun dépose un fichier de modifications dans `recherche/`. Un script de fusion applique ces modifications en refusant tout changement de chiffre v1.0 non autorisé. Un script de validation contrôle ensuite le résultat. Les deux scripts sont testés avant toute recherche.

**Pile technique :** Python 3.12, bibliothèque standard uniquement. Tests avec `unittest`.

**Spec :** `docs/superpowers/specs/2026-11-02-donnees-v1.1-design.md`

## Contraintes globales

- Python, bibliothèque standard seulement, scripts dans `scripts/`, tests dans `tests/`. Commande de test unique : `python3 -m unittest discover -s tests -t . -v`.
- Écriture de `metiers.json` : `json.dumps(d, ensure_ascii=False, indent=2)`, **sans** saut de ligne final. C'est le format exact de la v1.0 : un aller-retour sans modification doit redonner les mêmes octets.
- Le schéma v1.0 reste valide : on ajoute des champs, on n'en renomme ni n'en supprime aucun.
- Silkhom (brut annuel fixe) et Apec (fixe + variable, cadres) ne se mélangent jamais.
- Tout chiffre ajouté a une source. Tout rapprochement est déclaré : `{"de": <libellé exact>, "raison": <une phrase lisible par un étudiant>}`.
- Changer un chiffre déjà présent en v1.0 est interdit, sauf pour retirer une moyenne Silkhom introuvable (passage à `null`). Les autres changements de chiffres deviennent des propositions dans `relecture.md`.
- Un salaire obtenu par rapprochement plafonne `fiabilite` à `moyenne`. L'ordre est `nd` < `faible` < `moyenne` < `bonne`.
- Les textes Cigref et Silkhom sont paraphrasés, jamais recopiés.
- Le quiz s'appuie sur la vie d'étudiant (projets de groupe, TP, rendus, hackathons, projets perso, jeux, dépannage d'un proche, premières semaines d'alternance). Aucune situation ne suppose une expérience en entreprise. Le ton est le tutoiement, avec l'écriture inclusive des fiches (« Développeur·se »).
- `a_relire` n'est jamais modifié par ce plan.
- Identifiants des sources existantes : `cigref-2025`, `rome`, `silkhom-it-2026`, `silkhom-ia-2026`, `apec-2025`, `bdm-2026`.

## Points d'attention en revue

1. **Deux chantiers écrivent le même champ du même métier avec des valeurs différentes.** La fusion doit refuser le conflit au lieu de laisser gagner le dernier fichier lu. Testé en tâche 2 (`test_conflit_entre_chantiers_refuse`).
2. **Une modification vise un champ à l'intérieur d'un bloc `null`**, par exemple `salaires.apec.mediane` alors que `salaires.apec` vaut `null`. On attend un refus clair, sans plantage. Testé en tâche 2 (`test_parent_null_refuse`).
3. **Une fusion sans aucune modification ne doit pas changer l'encodage, l'indentation ni l'ordre des clés**, sinon le diff qu'Adrien relit devient illisible. Testé en tâche 2 (`test_aller_retour_identique`).
4. **Un rapprochement est ajouté sans que le badge de fiabilité baisse.** La validation doit le signaler. Testé en tâche 1 (`test_rapprochement_plafonne_fiabilite`).
5. **Une réponse du quiz a un poids hors de 1–2 ou vise une branche inconnue**, ce qui fausserait le top 3 en silence. Testé en tâche 1 (`test_quiz_poids_invalide`).

### Tâche 1 : script de validation

**Fichiers :**
- Créer : `scripts/__init__.py` (vide), `scripts/valider.py`
- Créer : `tests/__init__.py` (vide), `tests/fixtures.py`, `tests/test_valider.py`

**Interfaces :**
- Produit : `valider(donnees: dict) -> list[str]`. Renvoie la liste des erreurs, vide si tout va bien. Chaque message commence par l'`id` du métier ou par la clé de premier niveau concernée.
- Produit : `scores_max_quiz(quiz: dict, branches: list[str]) -> dict[str, int]`. Pour chaque branche, somme sur les questions du poids maximal que cette branche peut recevoir dans la question.
- Produit : en ligne de commande, `python3 scripts/valider.py <fichier>` affiche les erreurs, puis sort avec le code 0 s'il n'y en a aucune, 1 sinon.
- Produit : `tests/fixtures.py::donnees_valides() -> dict`. C'est un jeu v1.1 minimal et valide : 2 catégories, 2 macro-branches (une catégorie chacune), 3 métiers (l'un avec Silkhom et Apec complets, l'un avec `salaires.apec` à `null`, l'un d'évolution avec `depuis`), des voisins réciproques, 2 sources, et un quiz de 2 questions équilibré.

Règles que `valider` applique (copiées de la spec) :
- Clés de premier niveau présentes : `meta`, `categories`, `macro_branches`, `quiz`, `metiers`, `sources`.
- Chaque métier possède toutes les clés v1.0. `fiabilite` vaut l'une de ces valeurs : `bonne`, `moyenne`, `faible`, `nd`. `type` vaut `entree` ou `evolution`.
- Les références se résolvent : `categorie`, `depuis[]`, `voisins_meme_categorie[]`, `voisins_autres_categories[]`, et les `categories` de chaque macro-branche.
- Chaque catégorie appartient à exactement une macro-branche.
- Silkhom : pour chaque niveau et chaque zone, `min ≤ max`. Dans une grille, `annees_min` d'un niveau est supérieur ou égal à `annees_max` du niveau précédent (quand ce dernier n'est pas `null`). Si `moyenne_keur` n'est pas `null`, alors `moyenne_verifiee` vaut `true`.
- Apec : `d1 ≤ mediane ≤ d9`.
- Chaque bloc de salaires non nul possède la clé `rapprochement`, qui vaut `null` ou un dict avec `de` et `raison` non vides. Si un bloc du métier a un rapprochement, alors `fiabilite` vaut `moyenne`, `faible` ou `nd`.
- `rome` vaut `null` ou correspond à `^[A-N]\d{4}$`. `roadmap_url` vaut `null` ou commence par `https://roadmap.sh/`.
- Quiz : chaque `poids` vise une macro-branche existante, avec un poids entier de 1 ou 2, et chaque réponse vise 1 ou 2 branches. Les `id` de questions sont uniques. L'équilibre est vérifié par `(max(scores) - min(scores)) / max(scores) ≤ 0.10`.
- Compteurs : `meta.nb_metiers` égale le nombre de métiers ; `meta.nb_liens` égale le nombre de paires non orientées distinctes de voisins (la v1.0 donne 175) ; `categories[].nb` égale le nombre de métiers de la catégorie.

### Tâche 2 : script de fusion

**Fichiers :**
- Créer : `scripts/fusionner.py`, `tests/test_fusionner.py`

**Interfaces :**
- Consomme : `valider` de la tâche 1 (appelé en fin de commande), `donnees_valides()`.
- Produit : un format de fichier de chantier, `recherche/<chantier>.json` :
```json
{
  "chantier": "apec",
  "sources_ajoutees": [],
  "modifications": [
    { "metier": "mlops", "champ": "salaires.apec", "valeur": { "...": "..." }, "source": "apec-2025, famille « Développement informatique », p. 34" }
  ]
}
```
  `champ` est un chemin pointé depuis le métier. `source` est obligatoire et non vide. `sources_ajoutees` contient des entrées au format de `sources[]`.
- Produit : `normaliser(donnees: dict) -> dict`. Ajoute `"rapprochement": None` à chaque bloc `salaires.apec` et `salaires.silkhom` non nul qui n'a pas la clé.
- Produit : `appliquer(donnees: dict, chantiers: list[dict]) -> tuple[dict, list[str]]`. Renvoie les nouvelles données (l'entrée n'est jamais mutée) et la liste des refus.
- Produit : `fusionner(donnees: dict, chantiers: list[dict], macro_branches: list[dict], quiz: dict, date: str) -> tuple[dict, list[str]]`. Enchaîne `normaliser`, puis `appliquer`. Pose `macro_branches` et `quiz` en clés de premier niveau, insérées juste après `categories`. Ajoute les `sources_ajoutees` sans doublon d'`id`. Met `meta.version` à `"1.1"` et `meta.genere_le` à `date`.
- Produit : en ligne de commande, `python3 scripts/fusionner.py [--essai]`. Lit `metiers.json`, tous les `recherche/*.json` sauf `macro_branches.json` et `quiz.json` (lus à part), puis affiche les refus et les erreurs de `valider`. Sans `--essai`, et seulement s'il n'y a aucun refus, réécrit `metiers.json` au format de la v1.0. Code de sortie 1 s'il y a un refus.

Règles de `appliquer` (copiées de la spec) :
- Métier inconnu, source vide, ou parent `null` ou absent → refus.
- Valeur actuelle `None`, `[]`, `""` ou clé absente → la valeur est appliquée.
- Valeur actuelle égale à la nouvelle → rien à faire, pas de refus.
- Valeur actuelle non vide et différente → appliquée seulement si `champ` est dans `ECRASABLES` :
  - `fiabilite_note`, `salaires.silkhom.moyenne_verifiee`, `salaires.silkhom.moyenne_source` : appliqués librement ;
  - `fiabilite` : appliqué seulement si le nouveau rang est inférieur ou égal à l'ancien ;
  - `salaires.silkhom.moyenne_keur`, `salaires.silkhom.variation_pct` : appliqués seulement si la nouvelle valeur est `null`.
  - Sinon, refus avec le message `"<metier> <champ> : changement de chiffre v1.0, à proposer dans relecture.md"`.
- Deux chantiers posent sur le même `(metier, champ)` des valeurs différentes → refus pour les deux. Aucune des deux valeurs n'est appliquée.

  - `test_remplit_champ_vide` : `rome` de `None` à `"M1805"` → appliqué, aucun refus
  - `test_remplit_bloc_apec_null` : `salaires.apec` passe de `null` à un dict → appliqué
  - `test_parent_null_refuse` : `salaires.apec.mediane` alors que `apec` vaut `null` → 1 refus, pas d'exception
  - `test_changement_de_chiffre_refuse` : `salaires.apec.mediane` 50 → 52 → 1 refus contenant `"relecture.md"`, la valeur reste 50
  - `test_retrait_moyenne_autorise` : `moyenne_keur` 42.2 → `None` est appliqué ; 42.2 → 45.0 donne un refus
  - `test_fiabilite_ne_peut_que_baisser` : `bonne` → `moyenne` est appliqué ; `faible` → `bonne` donne un refus
  - `test_source_obligatoire` : `source: ""` → refus
  - `test_metier_inconnu` : refus contenant l'`id`

### Tâches 4 à 7 : chantiers de recherche

Ces quatre tâches sont indépendantes et se lancent en parallèle. Elles ne produisent pas de code, donc pas de cycle de tests. Pour chacune, le critère d'acceptation est le même :
- `recherche/<chantier>.json` passe `python3 scripts/fusionner.py --essai` sans aucun refus le concernant ;
- `recherche/<chantier>.md` existe et contient trois sections : **Choix faits**, **Cas douteux**, **Propositions de changement de chiffres** (pour chacune : métier, champ, valeur actuelle, valeur proposée, raison, source).

Règles communes à toutes les tâches de recherche :
- Ne jamais écrire dans `metiers.json`.
- Ne jamais inventer un chiffre. Si une source est inaccessible, le noter dans les Cas douteux et laisser `null`.
- Pour chaque `rapprochement` ajouté, ajouter aussi la modification `fiabilite` vers `moyenne` (si elle est au-dessus) et une `fiabilite_note` qui le mentionne.
- Une `fiabilite_note` contredite par les nouvelles données est corrigée, par exemple `test-manager`, « pas de ligne Silkhom dédiée ».
